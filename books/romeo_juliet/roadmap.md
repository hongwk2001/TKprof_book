## Product decisions

| Question | Decision |
| :--- | :--- |
| Main text | **Simplified modern English** for learners. This is the product; its quality matters most. |
| Engine | **Local gemma4:12b only** (no paid API). Its misreadings come from missing Shakespeare knowledge, so the lever is `glossary.json → gloss`, not a bigger model. |
| Second text | Korean, translated 1:1 from the simplified English |
| Third text | Shakespeare's original, kept in `raw`. Optional; not shown in v1. |
| Speakers | **Narrated by script** (`narrate.py`): `Sampson says, "…"` / `샘슨이 말한다. "…"`; asks/묻는다 on questions; Aside/Within/To X become "says to himself" / "calls from inside" / "says to Juliet". The model never adds names. |
| Stage directions | Narrated. Simple Enter/Exit/Exeunt with known names are written by script ("X enters." / "X가 들어온다."), and "Enter X" + X speaking merges into "X enters and says". The rest (~90, e.g. "Drinks.", "They fight.") are simplified by the model in Stage 4. |
| Chapters | One scene per chapter, 24 in all. The two Chorus prologues are folded into 1.1 and 2.1. |
| Free chapters | 3 (Act 1, Scenes 1–3) |

## Pipeline

```
raw speech (Shakespeare)
  → Stage 4  simplify: one LLM call returns a LIST of short modern sentences (1:N)
  → Stage 4b checks: sentence length, banned archaisms, names ⊆ raw names, nothing dropped
  → Stage 5  translate: each English sentence → one Korean sentence (1:1)
  → Stage 6  checks + human read
  → Stage 8  migrate_romeo_juliet.py → Book_apps assets (generated, never hand-edited)
```

Simplifying and splitting are one step. A separate splitting pass would have to guess where to cut sentences the model has just written.

### Stage 4 pilot findings (ch_07 balcony, ch_12 unseen)
- Without the gloss, gemma writes good plain English but misreads roughly 1 line in 10, e.g. "stumblest on my counsel" became "ignore my advice", and "Anon, good Nurse!" became "Come quickly".
- The gloss fixed most of those. But explaining a *famous line* in the gloss made gemma swap the explanation in ("A plague o' both your houses" became "A curse on…"). **The gloss explains single words only.**
- Shakespeare's "and"/"an" meaning "if" is a prompt rule, not a gloss entry: "and" is too common to gloss.
- **Measured over the whole play (Stage 6):** 44% of the 964 model-written items needed a fix (425 items, plus ~40 later old-word edits). The rate ran from about 25% in plain scenes (4.3, 5.2) to 45–50% in wordplay scenes (1.4, 2.4, 5.3). Typical misses were old usage ("Fast" = fast asleep, "doom" = sentence, "partizans" = followers), reversed sense ("Romeo dies" where Paris dies, a threat turned the wrong way) and literal puns. A clean check is **not** a correct translation: every scene was read against Shakespeare.
- Mechanical repairs are made before checking, never by the model: an entry ending in a comma is joined to the next one (lowercased unless "I" or a name), and a speaker cut off mid-line ends on "—".
- Retries keep the items that passed, re-ask only the failing ones, and tell the model what was wrong. The same prompt at low temperature gives the same answer.

### Stage 4 rules (simplified English)
- **Readability for ESL learners comes first**, above closeness to Shakespeare's wording. An old joke or rude pun becomes a modern equivalent the reader can follow (e.g. the medlar/"open-arse" joke becomes "that bottom-shaped fruit… a long, pointed pear"), never a vague stand-in like "a rude name".
- Target reading level B1 (intermediate): common words, active voice, at most ~20 words per sentence.
- No thou / thee / thy / art / doth / 'tis / wherefore / ere / nay / ay. Enforced by a check, not just the prompt.
- Keep meaning, not wordplay. When a pun can't survive, keep the plain sense and drop the joke.
- Never add a character name that isn't in the raw speech.
- Famous lines stay recognizable (e.g. "Romeo, Romeo, why are you Romeo?").

### Stage 5 rules (Korean)
- `glossary.json` names are mandatory.
- `register.json` sets polite speech or 반말 per speaker pair, e.g. Nurse→Juliet 반말 and Juliet→Nurse 반말 but affectionate. It is not written yet.

## JSON: the single source of truth

`json/ch_NN.json` is the **only** text file. There are no side files: no batch/result/preview `.txt` or `.json`, and no `work/` folder. Scripts either print to the terminal or write into `json/` directly. The only other outputs are the app assets, generated by the migrate script.

```json
{
  "id": 314, "tag": "P0314", "chapter_id": "ch_07",
  "act": 2, "scene": 2,
  "type": "speech",                 // header | speech | direction
  "speaker": "ROMEO",               // null for header/direction
  "raw": "But soft, what light through yonder window breaks?\nIt is the east, and Juliet is the sun! …",
  "sentences": [
    { "n": 1, "en": "But wait — what light is that in the window?", "ko": "…" },
    { "n": 2, "en": "It is the east, and Juliet is the sun!",      "ko": "…" }
  ]
}
```

- `en` and `ko` sit **in pairs** inside one list, so they can't drift out of alignment.
- `sentences == []` → Stage 4 outstanding; `ko == ""` → Stage 5 outstanding.
- `parse.py` refuses to overwrite a chapter that already has sentences or drafts.

### Model output goes straight into the item it belongs to

This is how shifting is prevented. Model output never goes to a separate file that must later be lined up with the play.

1. The request sends a scene's items **keyed by `tag`**: `{"P0313": "raw…", "P0314": "raw…"}`.
2. The model must answer with the **same keys**: `{"P0313": ["sentence", …], …}` (structured output, so no free text).
3. Before anything is written, the script checks that the set of returned tags is **exactly** the set sent: nothing missing, nothing extra, nothing reordered. Then it runs the Stage 4b checks. If any of these fails, the **whole scene is rejected and the file is untouched**.
4. Accepted output goes into that item's `drafts`, keyed by engine:

```json
"drafts": {
  "gemma4":  [{"en": "…"}, {"en": "…"}],
  "sonnet5": [{"en": "…"}, {"en": "…"}]
}
```

5. The pilot comparison is **printed** from `drafts`, never exported.
6. `promote.py <ch> <engine>` copies the chosen draft into `sentences` and deletes `drafts`, so a finished chapter holds one version only. Git keeps the history.

The Korean pass works the same way. The key is `tag` + sentence `n`, and the answer must return exactly one Korean line per English sentence, or the scene is rejected.

### Files

```
raw/pg1513.txt        download, never edited
parse.py              Stage 3: raw → json/ (speech / direction / header, + delivery)
narrate.py            json/ → narrated cards, printed only (`--json` for the exact app cards)
json/ch_NN.json       ← the ONLY text, tracked in git (drafts live inside it)
glossary.json         speakers (en/ko/gender), names, and `gloss`: Shakespeare word meanings for Stage 4
simplify.py           Stage 4: raw → drafts.<name> inside json/, whole scene or nothing
promote.py            chosen draft → sentences; drafts deleted
register.json         speech levels per speaker pair (TODO)
```

No `_v2`, `result_` or `fixed_` copies are kept in git. Fixes go into `json/`, then the migrate script is re-run. The app keeps `assets/books/_source.json` (source commit + per-file hash), and the migrate script refuses to overwrite an asset that was hand-edited since the last run.
